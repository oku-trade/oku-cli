# Security

## Privy delegated agent model

The account is the user's **external** Hyperliquid master wallet. It holds funds and signs `approveAgent` and builder-fee approval on the Oku authorization page, not in this binary. The trading agent is a distinct Privy **embedded** Ethereum wallet, approved by the master as a Hyperliquid named agent. Oku Agent stores no local agent private key. `oku orders submit` requests `eth_signTypedData_v4` from Privy for the Hyperliquid Agent domain (`Exchange`, version `1`, chainId `1337`, zero verifying contract), and locally recovers the signature against the approved embedded-wallet address before sending it to Oku.

**A readable credential permits signing anything the Privy grant allows on that embedded wallet until revoked.** Revocation may leave an existing access JWT valid for up to 15 minutes. Recommend a Privy policy limiting the wallet to `eth_signTypedData_v4` on that Agent domain. Host compromise, a leaked Linux passphrase file, or a compromised macOS Keychain item can bypass CLI safeguards. The CLI's digest, risk checks and confirmations are guardrails, not a security boundary. The embedded wallet should hold only funds deliberately allocated to agent EVM operations, with a strict Privy policy and minimal gas. Never mistake those balances for Hyperliquid master collateral.

## Credential storage

| Platform | Storage | Unlock |
|---|---|---|
| Linux | scrypt + XChaCha20-Poly1305 encrypted file | Masked interactive prompt, then cached in the kernel user keyring (same uid, never on disk, 8h TTL, `oku auth lock` clears it). Optional mode-0600 `OKU_PASSPHRASE_FILE` for unattended use. Opt-in unprotected mode (empty passphrase plus two typed confirmations) relies only on file permissions. |
| macOS | Keychain | Native Keychain authorization, no CLI passphrase. |

The credential contains Privy access and rotating refresh tokens and an Oku session token. Plaintext metadata binds profile, account, API origin, Privy app ID, agent address and wallet ID. A cross-process profile lock covers refresh and write-back: the rotated refresh token is saved before reuse. The short-lived Privy authorization key exists in memory only, never on disk. The Keychain service identifier and JSON schema version `oku.cli/v1` remain stable.

## Journal and MCP

`journal.sqlite` holds intents, action IDs and burned nonces, not credentials. `signing` holds the account gate while Privy signs; a signing failure or crash-left signing state can return to `created` without sending anything to Hyperliquid. Once `ConfirmAction` may have been sent, the action stays `submitting` or `unknown` until reconciliation. The gate is local to one machine: simultaneous use of the same Privy agent on multiple machines can collide on nonces or exposure.

MCP starts read-only; mutation tools require explicit enablement. Neither MCP nor the Service API runs `auth login` or `auth logout` or prompts for credentials. The user logs in from their own terminal. On Linux headless MCP access works while the credential is unlocked (`oku auth unlock` in the user's terminal), or with a user-supplied `OKU_PASSPHRASE_FILE`. While unlocked, any process running as the same user can use the credential, which is the same trust model as ssh-agent.

## Swap and bridge authorization limits

The EVM sender independently holds tokens and gas on each source chain. The master does not sign these transactions. Swap submission accepts only non-permit `fillQuoteEthToToken`, `fillQuoteTokenToToken`, or `fillQuoteTokenToEth` ABI calls to that chain's OkuRouter on any chain where Oku's swap markets are active. Each chain's router address comes from the shared `github.com/gfx-labs/chain-config/dist/networks` package (`Oku.Router`, the backend's source of truth; `0xb1f3a7B816B0681188F54dFa400991B93ADf00ed` on most chains, different on Mantle, Sei, Rootstock, Boba, BOB and others). A chain that is unknown, deprecated or has no router there is refused, and submit refuses an address without contract code on the chain. It verifies decoded input/output token, exact sell amount, recipient, value and exact ERC-20 router approval before broadcast. Quote simulation must succeed and quoted output must meet the prepared minimum, including a fresh selected quote. **OkuRouter does not enforce minimum output itself. The minimum inside aggregator swap calldata is constructed by the backend and is not independently decoded or verified by this CLI.** Trust in that backend is required. Bridge execution supports transaction-based bridge quotes from Oku. **Unlike swaps, bridge calldata, approvals, recipient, target contract, output minimum and economic effects are not independently verified by this CLI. The backend builds the calls, and the CLI executes them as returned, matching the Oku web app's backend trust model.** Review the route, recipient, quoted minimum, source and destination before signing, and use a trusted backend. Intent-based and typed-data signing routes are skipped. Approval and bridge calls execute atomically in one batch when more than one call is supplied; the source chain is checked for structural executability and gas/balance preflight, not bridge correctness. Source confirmation does not prove destination fill. `bridge status` checks Across's read-only status API for Across routes only on a best-effort basis (`OKU_ACROSS_API_URL` override), reporting unknown on outage without changing source state; all routes show backend Ping status. Verify destination funds independently.

A swap that needs an approval is sent as one atomic Privy `wallet_sendCalls` batch `[approve exact amount to OkuRouter, verified swap]`. Privy upgrades the agent wallet with EIP-7702 to a Kernel smart account on first use; the address is unchanged. The approval can never confirm without its swap. A single-step route, including native ETH input, sends one normal transaction. Submit waits for the chain's confirmation depth: typically under a minute on fast L2s, several minutes on Ethereum, Polygon or BNB Chain. If the wait ends first, the intent stays unresolved and `status` finishes it; never resubmit. Before submission the CLI records the agent nonce and block; `oku swap status --intent ID` can find the batch by nonce even without a returned hash, then confirm its receipt. The batch is accepted only if it is the agent's self-call carrying every journaled call target and calldata. Batch lookup needs historical account state for recent blocks; the default Oku eRPC gateway serves it, and any `OKU_RPC_URL_<CHAINID>` override must too.

RPC reads default to Oku's eRPC gateway `https://erpc.lat.gfx.town/main/<name>`, where `<name>` is the chain's internal name in the shared chain-config networks package (e.g. `arbitrum`, `base`); it serves receipts and the recent historical state that batch lookup needs. A chain unknown or deprecated in chain-config requires `OKU_RPC_URL_<CHAINID>`; `send`, `swap` and `bridge` refuse a chain with neither before contacting the backend (`wallet balances` reads through Oku and needs no RPC). Override any default the same way. The endpoint is trusted for balances, estimates, transaction evidence and settlement. The CLI checks `eth_chainId`, receipt hash and canonical block hash, and waits for 12 confirmations on Ethereum, 64 on BNB Chain and Polygon, and 20 elsewhere (override `OKU_RPC_CONFIRMATIONS_<CHAINID>`). **One malicious endpoint can still fabricate internally consistent responses**; use a trusted RPC and independently verify high-value transfers. Gas preflight estimates each exact transaction with `from=agent`, adds 30% gas and uses an EIP-1559 fee cap or gas-price fallback across steps. Privy may choose different fees, and L2 L1 data fees can differ. This is not a guarantee of inclusion or affordability.

`INSUFFICIENT_GAS`, `INSUFFICIENT_BALANCE`, or `REJECTED` with “nothing broadcast” closes the intent and permits a new prepare after correcting the cause. An `OUTCOME_UNKNOWN` broadcast must never be retried or replaced: one unresolved intent blocks new onchain intents for the agent. Start with `oku swap status --intent ID` for a swap. For a hash recovered independently, `oku send reconcile --intent ID --tx-hash TX_HASH` or `oku swap reconcile --intent ID --tx-hash TX_HASH` checks the chain, sender, destination, value and input bytes against the journaled transaction (for a batch: the agent self-call containing every journaled call) before attaching the hash. It only resolves after a sufficiently confirmed receipt; a missing or invalid receipt retains the unresolved gate.

## Independent revocations

The Privy embedded agent wallet now has **EVM spending power independent of Hyperliquid agent trading limits**. Hyperliquid order limits and agent revocation do not protect ERC-20s or native gas held in this wallet. The Privy wallet policy must allow `eth_sendTransaction` for ordinary transfers and single-step swaps and `wallet_sendCalls` for approval+swap batches on the intended chains and contracts; restrict grants tightly and do not store more value in the agent wallet than needed. Keep native gas, such as ETH on Arbitrum, available for sends and swaps. Both RPC shapes have been exercised live with a funded agent wallet on Arbitrum (send, deposit, single-step swap and approval+swap batch). A receipt confirms an EVM transfer, not Hyperliquid credit to the master.

`oku auth logout` tries Oku session logout and Privy grant revocation on a best-effort basis, reports those outcomes and deletes the local credential. **It does not revoke the Hyperliquid agent approval, cancel orders or close positions.** Revoke the HL agent separately with the master wallet on Hyperliquid or the Oku page. Revoke any other device grants separately. Uninstalling the binary does none of these operations and does not delete journal history or backups.
